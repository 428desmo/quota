# インターネット対戦の拡張案

2026-10-15 作成。実装前の検討文書。現行仕様は `tools/serve_unity_web.py` と `unity/Assets/Scripts/Quota/TableView.cs` を確認した。ここでの「推奨」は採用済みの仕様ではない。

## 目指す対局の入り方

インターネット通信を選ぶと、まず「公開卓を探す」「卓IDで参加」「新しい卓を作る」を選べる。公開卓では募集中・空席ありの卓を一覧から選ぶ。卓IDが分かれば一覧を経由せず入れる。新しい卓は作成時に「公開」か「非公開」を選び、作成後に卓IDと共有操作を表示する。非公開卓にはIDを知る人だけが入れ、リーダーは募集中に非公開から公開へ変更できる。公開後は残りの人間用の席を公募する。

卓への入室時に「プレイヤーとして参加」「観戦」を明示する。空席がない場合に黙って観戦へ切り替えない。対局中の卓は観戦のみとし、退席者の再参加は元の席を優先する。現在の3・4人制、CPUが残席を埋める仕組み、リーダーだけが設定・開始する原則は当面維持する。

「公開」は発見できること、「参加可能」は空席と参加許可があることを別の状態として扱う。たとえば公開・満席の卓を一覧に残すなら「観戦のみ」と表示する。公開卓の一覧が大きくなったら、募集中を先頭に、人数・観戦可否などで絞る。初期版では検索や自動マッチングは不要。

## 公開範囲と卓ID

- **公開卓**：一覧に卓名またはリーダーの表示名、募集状況、空席数、人数、ラウンド数、手番タイムアウトを出す。IDでも参加できる。一覧にはプレイヤーの識別子や接続先IPを載せない。
- **非公開卓**：一覧・件数・検索結果から存在を漏らさない。IDを入力した場合だけ参加できる。観戦も同じ条件にするか、リーダー承認制にするかを決める。初期案は「ID保持者は観戦も可」。
- **公開状態の変更**：募集中の非公開→公開はリーダーがいつでも可能。公開→非公開も募集中だけ可能とし、既に入った参加者は維持する。対局開始後の変更は初期版では不可とする。
- **共有**：IDのコピーと、可能なら招待リンクのコピーを用意する。招待リンクを踏んでも即参加させず、卓情報と「参加／観戦」を確認してから入る。リンクを外部へ貼ると転送・履歴等に残り得るため、取り消し・再発行も検討する。

現行サーバの卓IDは `secrets.token_hex(3)`、つまり24ビット（6桁の16進数）。非公開卓の入場資格としては短すぎる。非公開卓については、公開しても差し支えない内部IDと、十分に予測しにくい招待コードを分離するか、共有する卓ID自体を長い乱数にする。初期案は**卓IDとは別に128ビット以上のランダムな招待コードを発行**し、非公開卓の参加・観戦に必須とする。画面上の「卓IDで参加」は、利用者には一つのコード入力欄として見せてもよい。公開卓は一覧から参加でき、招待コードを知らなくても入れる。コードは対局終了・卓削除で失効し、リーダーが再発行できるようにする。誤入力や失効時は同じ程度の情報量のエラーにする。推測試行にはレート制限をかける。[OWASPのセッションID設計](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)は予測困難な識別子の参考になる。

招待コードを長くすると手入力は不便になる。まずはコピー・共有リンクを主導線とし、短い手入力コードは招待承認、期限、試行制限を含む別設計として後から検討する。短い表示用卓番号だけを秘密として扱わない。

## ロビーと席の扱い

卓状態は「募集中」「対局中」「終了」に分ける。募集中には総席数、参加中の人間、残りの人間が入れる席、CPUで埋める予定の席、観戦者を別々に示す。CPU枠は開始前なら人間が入れる。リーダーが「残席を募集する／ここでCPUを確定して開始する」を判断できると、非公開から途中公開する意図が伝わりやすい。

同時に最後の席へ複数人が入ろうとした場合は、サーバが原子的に先着を決め、遅れた側には「満席。観戦する？」を表示する。参加ボタンを押した後の通信再試行で二重着席しないようにする。同一利用者の多重タブをどう扱うかも決める。初期案は同じ利用者のアクティブ操作を一端末に限定し、別タブでの参加は既存タブを観戦にするか、明示的な引き継ぎ確認を出す。

リーダーが募集中に退席した場合は、参加時刻順で次の人間プレイヤーに権限を移す。全員いなくなれば短い猶予後に卓を閉じる。対局中は現在のCPU代行・再参加を維持し、リーダーが不在でもラウンドが進むようにする。卓が公開か非公開かにかかわらず、元のプレイヤーの席は再参加のために保持する。再参加資格を表示名では判定しない。

開始条件として、少なくともリーダーが人間プレイヤーの人数・CPU補充・ラウンド数を確認する。必要なら参加者の「準備完了」を後から加える。初期版では開始前の確認ダイアログで十分かもしれない。CPUのみの模擬戦は公開卓の募集には出さず、作成者のローカルな入口と区別する。

## 観戦・公平性・再参加

観戦者が見られる情報を明文化する。初期案はプレイヤーと同じ公開盤面、手番、行動通知、得点のみ。未公開の山札順、除外札、乱数状態、秘密の操作資格は送らない。観戦者の上限を設け、満員なら入場を断る。観戦の途中入退室は対局を止めない。非公開卓の観戦権は招待コードを持つ人に限る。

現在の `UnityTable.recruiting()` は `seed` と全行動履歴を参加者へ返す。ゲームが同じシードから札を再現できるなら、通信内容から将来の山札や除外札を推測できる可能性がある。**公開対戦を始める前に、サーバだけが非公開乱数と山札を保持し、クライアントには各時点で見えてよい状態だけを返す方式へ移す必要がある。** アクション履歴を送るとしても、隠し情報を再構成できない形式にする。これはCPUの不正な先読み防止にも関わる。

回線断と明示的EXITを区別する。通信断では席を即放棄させず、既存の手番タイムアウトとCPU代行で進め、同じ資格の利用者が戻れば次の適切な手番から復帰させる。明示的EXITでも、再参加を許す現在の仕様を基本とする。再参加時に進行中の対局データが多すぎないよう、最新の公開スナップショットと必要な差分だけで復元できる形を検討する。

サーバ再起動では現行のメモリ内の卓が失われる。長時間対戦を公開するなら、卓の状態・参加資格・非公開乱数・期限を永続化して復旧するか、「再起動時は対局が終了する」と利用者に明示するかを選ぶ。初期公開版では後者でも始められるが、運用のたびに卓が消える設計は早期に解消したい。

## 名前・利用者識別・迷惑行為

表示名には文字数上限に加え、空白や制御文字、ゼロ幅文字、紛らわしいUnicode、HTML等の表示上の問題を検査する。禁止語は差別・脅迫・露骨な性的表現、運営や他人へのなりすましなどのカテゴリを定義し、管理可能な辞書で運用する。ただし辞書だけで全表記ゆれを防げないので、単純な部分一致による誤検知に注意する。正規化して判定し、拒否時は理由を短く示して名前の変更を促す。公開一覧・ロビー・対局画面・ログで同じ表示規則を使う。通報、ミュート、名前の変更を後で導入できるようにする。

表示名は本人確認にならない。現状は端末保存のGUIDを `X-Quota-Client` ヘッダーで自己申告しており、サーバはそれを実質的なプレイヤー識別に使う。別のクライアントが同じ値を送れば、席のなりすましや操作につながる可能性がある。**公開運用ではサーバ発行・検証の参加資格を持たせ、卓ごとの参加・再参加・リーダー操作をサーバで認可する。** 初期版はアカウントなしのゲスト資格でもよいが、ブラウザのデータ消去で資格が失われる点を説明する。複数端末で同じ席へ戻る機能、恒久的な戦績、強い制裁が欲しくなればアカウント方式を検討する。

名前の禁止語に加え、公開卓名を導入するなら卓名も同じ基準で検査する。初期版は自由記述の卓名を設けず、リーダー名と卓の設定値だけで一覧を構成してもよい。リーダーが参加者を退出させる機能は嫌がらせにも使えるため、採用するなら理由の通知、対象者の再入場条件、対局開始後の制限を決める。

「途中離脱したらしばらく参加禁止」は、**最初から導入しない**案を推奨する。iPhoneのタブ破棄、通信断、サーバ不具合、単なるEXITを正しく区別できず、アカウントなしでは容易に回避される。代わりに、対局中の明示的EXIT回数や短時間の卓作成・退出の繰り返しを計測し、まずは警告、同じ卓への再参加待ち時間、公開卓の作成頻度制限などの軽い措置を検討する。回線断や手番タイムアウトは制裁対象にしない。罰則を設ける場合は条件、期間、解除方法、誤判定時の扱いを先に公開し、再参加の権利との整合を取る。

## 運用・負荷・プライバシー

公開卓の作成、卓IDの試行、参加／退出、観戦、状態ポーリング、名前変更にそれぞれ適切な上限を設ける。個人単位だけでなくIP単位の上限も検討するが、共有回線の巻き添えに注意する。最大卓数、卓ごとの観戦者数、放置した募集中卓の寿命を決める。高負荷時は新規卓作成を先に制限し、進行中の対局を優先する。[OWASPのAPI資源制限の整理](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)も参照。

現行の卓は最終アクセスから180秒で削除される。これはブラウザの一時中断やサーバ再起動と合わせて再検討する。作成直後・募集中・対局中・終了後で期限を分け、期限が近いときは画面で知らせる。進行中の卓については、誰も見ていなくても一定時間CPU代行で進めるか、休止するかを決める。サーバ資源保護のため無期限に保持しない。

測定値は公開卓数、空席数、作成・参加成功率、招待コード失敗率、切断・再参加率、卓の寿命、同時観戦者数、APIの遅延・エラー率などに絞る。プレイヤー名、招待コード、識別資格、行動本文を通常のメトリクスに含めない。今の診断ログにはクライアントIDやIP等が出るため、保存期間とアクセス権を決め、公開運用前に必要最小限へ整理する。通信はHTTPSを前提とし、招待情報をURLに入れる場合は外部サイトへの参照元送信やログ記録を考慮する。

## 実装の順序案と確認事項

1. **公平性と認可の土台**：隠し情報をクライアントへ出さず、サーバ発行の参加資格で席・リーダー操作を保護する。既存の公開対戦にも効く修正。
2. **公開／非公開と入室導線**：卓の可視性、長い招待コード、公開一覧の絞り込み、卓ID入力、非公開→公開、空席競合時の処理を加える。
3. **継続性と運用**：卓の期限、切断復帰、サーバ再起動時の扱い、レート制限、名前の検査、基本メトリクスを整える。
4. **利用状況に応じた追加**：準備完了、通報・ブロック、観戦制御、アカウント、戦績、段階的な迷惑行為対策を評価する。

仕様決定前に特に答えが必要なのは、(a) 非公開卓の観戦をコード保持者に許すか、(b) 公開卓では誰でも観戦できるか、(c) 人間用の席を何枠まで残したまま対局を始められるか、(d) リーダー不在時に誰が卓設定と次ラウンドを進めるか、(e) サーバ再起動後に進行中の卓を復旧するか、の5点。初期案は本文のとおりとし、実装に入るときに確定する。
