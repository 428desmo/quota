# CPU戦術の対照シミュレーション

[`cpu_tactics_catalog.md`](cpu_tactics_catalog.md) に列挙した候補の効果を検討するための実験用ツール。対局中のCPUやルール、既存の `cpu_ranking_v1.2.json` は変更しない。

## 何を比較するか

`tools/tactic_simulator.py` は、同じ乱数種・同じCPUキャラクター・同じ席を使う対照戦と候補戦を1組とする。候補戦では**指定した1席だけ**に候補戦術を足し、ほかの席は既存CPUのままにする。各乱数種について候補席を3席または4席すべてに移して繰り返す。ラウンド数の既定は人数分、並び順・称号・特殊行動ルールは有効。対照戦の `--policy baseline` は完全な無変更の検査用。

同じ乱数種により**最初の配札と手番順は一致する**。候補が異なる行動を選んだ後は、場札や山札の引かれ方、対戦相手の応答も変わり得る。そのため、以後の札配置が同一であることは保証しない。これは同じ開始条件からの対局全体の差を測る試験である。単一局面での最善手を証明するものではない。

CPUキャラクターは乱数種ごとに既存の全組合せから一様に選ぶ。`rate_cpu.py` の順位データを読み込んだり、記録を加算したりしない。実際の卓でのCPU選出比率や人間の判断を再現する試験ではない。

## 実行

リポジトリのルートから実行する。依存ライブラリは標準ライブラリのみ。

```bash
python3 tools/tactic_simulator.py --policy baseline --deals 10 --seed 42
python3 tools/tactic_simulator.py --policy P11 --deals 1000 --seed 42 \
  --players 3 --rounds 3 --json-out /tmp/quota-p11.json
python3 tools/tactic_simulator.py --policy P12 --deals 1000 --seed 42 \
  --players 4 --rounds 4 --json-out /tmp/quota-p12.json
python3 tools/tactic_simulator.py --policy A15 --deck-threshold 30 \
  --deals 1000 --seed 42 --json-out /tmp/quota-a15.json
```

`--deals` は独立な開始条件の数。対局数は `deals × players × 2`（対照と候補）。同じ `--seed`・人数・ラウンド数を固定して異なる候補を比べる。全候補のパラメータを同じデータで選び直すと過適合しやすいので、採用判断では別の乱数種でも再試験する。

現在の候補は**実装方法の試作品**であり、カタログで提案した戦術の完成版ではない。

| 指定 | 試作品の内容 |
|---|---|
| `baseline` | 何も変更しない。差が0になることを確認する。 |
| `P11` | 自分があと1枚で完成し、同じ種類のノルマを持つ相手がいるとき、自分の隣接数字ボーナスと相手の隣接数字ボーナスを失わせる効果を比較する。相手の長期的な完成確率までは評価しない。 |
| `P12` | 終盤（山札24枚以下）で、既存CPUがパスまたは公開札から完成可能とは言えないノルマを選ぶ場合、相手の必要な種類の札を、**公開情報から自分には完成不能と確定できるときだけ**妨害ノルマにする。 |
| `A15` | 山札が指定枚数以下になるまで配り直し・ダブルを使わない固定閾値の例。将来の難局を予測して権利の価値を求める完全なモデルではない。 |

## 結果の見方

- `mean_score_delta`：候補席の最終得点から対照戦の同じ席の最終得点を引いた平均。正なら候補が高得点。相手の得点変化は直接は表さない。
- `mean_win_share_delta`：1位の取り分の差。単独1位は1、同率1位が2人なら0.5、1位以外は0とする。妨害戦術はこちらも重要。
- `mean_margin_delta`：候補席の得点から最も得点の高い相手の得点を引いた差が、対照戦よりどれだけ変わったか。
- `score_delta_95ci_by_deal` / `win_share_delta_95ci_by_deal`：同じ乱数種の各席を1つのブロックとして計算した、簡易的な95%信頼区間。`null` は独立な開始条件が1つしかない場合。0をまたぐ場合、今回の試験だけでは改善・悪化を決められない。0をまたがなくても、このCPU集団・ルール・戦術パラメータに対する結果であり、一般的な最適性の証明ではない。
- `candidate_applicable`：戦術の条件が成立した意思決定回数。`candidate_changed`：実際に既存CPUの選択を変更した回数。両方が少ないと平均差は解釈しにくい。
- `candidate_special_offered` / `candidate_special_blocked`：配り直し・ダブルの使用候補が出た回数と、候補戦術が使用を止めた回数。A15で主に使う。
- JSONの `trials` には開始乱数種、キャラクターID、候補席、対照/候補の得点・勝利取り分・達成回数・判断回数を保存する。異常な対局を同じ開始条件で再現できる。

**適用回数と行動変更回数が十分に出るまで、平均得点だけで採否を決めない。** 試作品の閾値や重みは評価前の仮置きである。

## 新しい戦術を差し込む

`tools/tactic_policies.py` の `Policy` を継承し、`decide(observation, baseline_action) -> Decision` を実装する。`Decision(applicable=True)` は条件が成立したことを記録する。`allow_special(observation, kind)` を実装すると、`reshuffle` または `double` の宣言を拒める。カード履歴が必要な戦術は `on_transition(before, after, action, phase)` で各人の公開状態変化を記憶する。`phase` は `declaration`（特殊行動宣言や配り直し）、`action`（カード取得・放棄・パスと自動処理）、`new_round`。候補ポリシーは各対局で新しいインスタンスを作るので、ラウンド内記憶を対局間で漏らさない。

別モジュールにファクトリ関数 `policy()` を置き、`--policy package.module:policy` で読み込むこともできる。ファクトリは毎対局、新しい `Policy` インスタンスを返す。候補が返す行動は必ず合法か検査され、違反時には試験を停止する。

ポリシーに渡す `Observation` は場札・捨て札・各人の公開札と得点・山札**枚数**・手番順・膠着状態・合法手だけで構成される。山札の内容/順序、伏せた除外札、乱数生成器は渡さない。物理カードのIDは合法手を指定するために含むが、種類・数字が同じ2枚を公開情報から区別できると仮定して推測しない。`legal_actions` の収集手はカードの組だけを列挙する。取得順を変える戦術は、その組の順列を `Collect` に指定でき、エンジンの合法性チェックが検証する。公開イベントからのカード記憶も、配り直し時に戻った札を永久除去と誤認しないようにする。

この仕組みで測るのは**既存CPUに戦術を1件追加したときの差**である。戦術を複数同時に足した相互作用や、ルール変更後の再調整は別の条件として測る。
